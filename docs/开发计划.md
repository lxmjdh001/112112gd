# gongdan007 开发计划

网站统一管理业务，员工通过长期登录码使用桌面客户端，聊天区域直接加载 WhatsApp 官方 Web 页面。先交付登录码、代理、平台登录和后台状态同步，再扩展完整中后台业务。

计划日期为 2026 年 10 月 9 日。项目目录为 `/Volumes/Lexar/web/gongdan007`。本轮交付为目录、选型、开发计划和验收定义；各业务阶段仍待实施。

## 一 产品范围与术语

| 对象 | 定义 |
| --- | --- |
| 平台运营后台 | 系统运营方管理租户、套餐、审核、系统参数与平台运行情况 |
| 客户管理中台 | 企业或团队管理自己的登录码、员工设备、平台账号、代理及客户资料 |
| 员工席位 | 一个可追踪的工作身份，由后台创建，可以只填写姓名或备注，不要求员工注册账号密码 |
| 登录码 | 席位对应的客户端登录凭据，在有效期内可反复使用，可限制设备数量、平台和账号额度 |
| 平台账号 | 员工在客户端实际登录的 WhatsApp 等账号，不是网站用户，也不是登录码 |
| 推广码 | 用于推广归因和返佣，与客户端登录码分别管理 |
| 底库 | 已有联系人和历史线索的查重数据集合；用户输入的“底裤管理”统一命名为“底库管理” |
| 线索 | 一次新增客户接触或导入形成的业务记录，记录来源、归属及查重结果 |
| 客户 | 可持续维护的客户资料，关联多个线索、联系方式和跟进记录 |

网站使用一套中后台应用，通过角色与租户切换展示运营后台或客户中台。员工默认只有客户端权限；员工的网站访问能力按角色单独授予。

首版提供 Windows x64、macOS Apple 芯片与 Intel 版本。聊天界面、输入框、会话列表、文件收发等由官方网页呈现。自有客户端界面包括登录码输入、平台账号切换、连接状态、代理摘要和必要的故障操作。

## 二 技术与部署方案

| 层 | 选择 | 用途 |
| --- | --- | --- |
| 中后台 | Vue Vben Admin 5 系列的 Element Plus 版本，Vue 3 与 TypeScript | 菜单、页签、列表、搜索、表单、弹窗、权限展示 |
| 网站服务端 | Go 与 Gin | 业务接口、认证授权、设备管理、任务与事件处理 |
| 数据访问 | PostgreSQL 与 GORM，版本化 SQL 迁移 | 业务数据、权限、账本、登录日志、同步事件 |
| 客户端 | Electron 与 TypeScript，Vue 3 外围界面 | 嵌入官方网页、独立会话、账号切换、代理控制 |
| 实时通信 | HTTPS 与 WSS | 配置更新、状态上报、远程撤销与执行回执 |
| 文件 | 初期本地受控存储，保留 S3 兼容接口 | 导入文件、导出文件及后续媒体归档 |
| 运行环境 | Linux VPS、反向代理 HTTPS、Go 服务与 PostgreSQL | 网站业务部署；平台网页运行在员工电脑 |

客户端通过 `WebContentsView` 加载 `https://web.whatsapp.com/`，每个账号分配独立持久化 Session。官方网页的登录凭据保存在客户端，不由中后台持有。[Electron WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view)、[Session](https://www.electronjs.org/docs/latest/api/session)

Go 承担服务端业务。Electron 自带 Node.js 运行环境来管理浏览器，不要求客户另外安装 Node.js。此次原生网页方案不同时运行另一套 WhatsApp 协议登录，避免同一产品存在两条不一致的登录流程。

网站的业务模块先部署为一个 Go 服务，定时任务与事件队列使用同一数据库的可靠任务记录。服务之间的接口清晰后，可按负载单独部署归档、导入或统计任务，不把初期部署拆成大量服务。

## 四 登录码与设备规则

已确认采用长期登录码。后台先创建席位，再为席位生成随机登录码；代码可分组显示，支持复制、批量分发和重新生成。服务端保存不可逆校验值，明文仅在生成或重置后交付；列表常态展示码编号和掩码，查询按编号、员工、分组或备注进行。

登录码属性包括有效期、启用状态、绑定设备上限、允许的平台、各平台账号额度、客户组织和所属员工。设备上限默认按“已授权设备”计算，另展示当前在线设备数，防止通过离线不断占用新设备。

客户端首次输入登录码后向服务器校验，在数据库事务中占用设备名额；同时请求不能突破上限。设备以安装实例和本机密钥标识，不使用固定硬件指纹作为唯一依据。设备会话保存在系统安全存储中，后续打开客户端自动恢复登录。登录码不作为每个接口反复传输的令牌。

后台支持停用、到期、重置和解绑。默认重置登录码同时撤销该席位旧设备会话，保留席位、账号和客户的业务 ID；重新授权后同一安装实例恢复已有本地配置。解绑设备释放授权名额，平台会话是否在远端同时注销需要独立操作与回执。

在线客户端收到撤销通知即停止工作；失联客户端在短授权租约到期后暂停平台页面，重新联网校验后恢复。初始参数建议心跳 30 秒、状态过期 90 秒、离线授权租约 5 分钟，可配置并在界面说明。撤销不能保证使已经断网的电脑瞬间执行命令。

网站运营管理员与客户管理员使用单独的网站身份验证。员工客户端只有登录码入口；登录码权限不得调用管理后台的管理接口。

## 五 WhatsApp 原生网页接入

第一阶段客户端进入系统后，读取后台分配的账号名额与代理配置，创建账号槽位，再加载官方 WhatsApp Web。二维码、手机关联操作、登录后的聊天界面全部由官方网页提供。

平台适配器只负责必要的页面生命周期、账号身份识别、状态识别和可选数据采集。适配器按独立版本维护；页面结构变化时可以关闭失效的数据采集功能，保留正常原生聊天。官方网页在 Electron 的实际兼容性通过小样先验证，不以能打开页面替代扫码与持续在线测试。

| 状态维度 | 示例 | 展示原则 |
| --- | --- | --- |
| 客户端连接 | 在线、失联、撤销、到期 | 来自服务器会话及心跳 |
| 平台授权 | 未登录、待扫码、已登录、需重新登录、未知 | 来自当前官方网页的授权状态 |
| 平台连接 | 连接中、在线、重连中、代理异常、断网、未知 | 登录凭据存在不等于当前网络在线 |
| 上报新鲜度 | 最近确认时间、过期 | 过期状态标记为待确认，不推断手机已退出 |

平台账号手机号和昵称尽量从实际登录信息识别；页面无法可靠提供时显示未获取并允许业务备注。官方页面变更时，状态检测失效显示未知，不自动清除账号资料或强制退出。

第一次加载账号时即设置代理并完成校验。每个账号使用不同 Session，Cookie、LocalStorage、IndexedDB、缓存与 Service Worker 按账号分区。代理绑定变化后关闭旧连接并按新配置重新建立，防止旧连接继续使用原出口。

这是浏览器会话与指定代理的隔离。多个账号仍可能共享操作系统、Chromium 版本和某些设备特征；不能承诺独立物理设备或完全不同指纹。Electron 的 Session 分区也不等于操作系统级网络沙箱。

平台 HTTP、WebSocket、媒体与相关子资源都要验证是否遵循代理。对 WebRTC 直连能力采用受限策略，首版通话兼容性另测。代理失败不允许静默回退直连。若实测 Session 配置仍存在不可控出口，须采用独立浏览器进程与系统网络限制后再验收“强网络隔离”；Windows 与 macOS 分别验证。

暂停账号会停止该页面连接；退出整个客户端或电脑休眠会影响实时收发。为控制本机资源，区分保持在线与暂停账号，不能把隐藏页面宣称为零资源占用。

## 六 聊天归档和客户数据

原生网页显示聊天，与网站获取聊天内容是不同能力。账号列表的基础身份和状态先实现；客户运营中的聊天记录、实时线索查重与敏感内容监控，依赖后续的数据采集能力。

为每个平台声明 `identity`、`connectionState`、`contacts`、`liveMessages`、`history`、`media` 等能力。首个验证阶段确定 WhatsApp 哪些数据可以稳定获取、读取范围和缺口。只有通过真实账号验证的能力才标记为可用；样例和模拟数据只在开发环境展示。

后续归档先覆盖可靠获得的文字和事件，保存来源平台消息 ID、账号 ID、方向、时间、内容版本以及采集范围。本地使用待上报队列；服务端以事件 ID 幂等入库，断网恢复补传。历史回填与实时消息分开进度，未同步区间明确显示，不能把少量可见页面消息当成完整聊天历史。

号码与平台内部标识分开存储。仅根据平台提供的可信对应关系合并 WhatsApp PN 与 LID；同名联系人不自动合并，不把 `@lid` 前面的数字直接当作手机号。线索查重优先使用规范化号码和平台标识，保留原始值、匹配依据和导入来源。

客户资料、联系人底库、线索与聊天归档均带租户边界和归属权限。平台登录凭据、Cookie 和完整浏览器目录不上报网站。对外导出、聊天查看和敏感字段读取单独记录审计。

若原生网页无法稳定提供所需数据，应展示具体能力限制，使用授权导入或另行验证可用的数据接入方式；不能以完成页面菜单代替归档与内控的实际功能。

P1 是技术前置阶段，P2 到 P4 构成第一版可用业务。第一版的完整演示路径为：后台创建席位和登录码 → 配置代理 → 客户端输入码 → 打开官方 WhatsApp 网页扫码 → 后台显示所属账号与状态 → 停用或重置后权限生效。

P5 到 P7 补齐此次提出的全部中后台模块。P6 的完成取决于 P1 对数据采集的验证结论。先完成资料、标签、跟进等独立能力，同时把不支持的归档范围列为明确缺口。

各阶段结束提供可运行版本、变更清单、验证结果、已知限制和对应提交号。排期按阶段估算，在 P1 完成后依据兼容性和采集结果细化；不在尚未验证官方网页兼容性的情况下承诺全部功能固定天数交付。

## 八 模块化与新平台扩展

服务端按认证、租户、登录码、设备、平台账号、代理、底库、线索、客户、归档、内控、账户和推广拆分模块。每个模块拥有自己的接口、业务逻辑、数据模型和测试；跨模块通过公开服务接口或事件协作。

客户端把主进程、受限桥接和外围界面分开。平台相关 URL、弹窗策略、账号信息识别、状态检测与采集逻辑集中到平台适配包，不放到账号列表或主窗口组件中。

新增一个平台需要：注册平台标识与允许域名，声明支持的能力，实现页面生命周期及必要检测，接入额度与代理策略，完成平台专项测试，再在后台开放该平台。未接入的平台不会出现在可用平台选项中。

中后台的菜单、权限点、接口和数据字典以模块清单为索引。模块化采用编译时组合与版本化发布，初版不提供任意远程代码插件执行。

## 九 页面规范

网站使用紧凑的业务后台布局：左侧模块菜单、顶部页签、页内统一标题、筛选区、操作区和数据表格。账号与代理列表支持列显隐、横向滚动、分页、批量操作和空状态。

正文和表格建议 13 至 14px，辅助文字 12px，页面标题 18 至 20px，控件高度 32 至 36px。统一设计变量，不对所有元素机械减字号。大列表保持固定表头，表格密度可切换。

新增或编辑使用统一抽屉或弹窗。短操作菜单支持点击外部和 Escape 关闭；有未保存编辑时给出明确提示。批量导入先预览识别结果，显示行号、错误原因、重复情况和成功失败数量。

官方聊天页面保持其原有排版与交互，自有字号规范只作用于网站和客户端外围。平台网页提供的二维码只在本机原生登录页显示；账号列表不长期保存或展示可用于登录的二维码。

## 十 质量与数据要求

必须验证：重复请求幂等、跨租户越权、登录码并发使用、设备上限竞争、撤销与到期、两账号会话隔离、代理故障、页面状态过期、导入查重、断网补传、钱包流水一致性和备份恢复。

稳定性测试使用专用测试账号，覆盖连续运行 24 至 72 小时、应用退出重开、电脑休眠唤醒、代理断网恢复、后台短时不可达、平台页面变更识别失败。记录每种故障对应的界面状态与恢复方式，不以页面仍然可见作为在线依据。

基础性能记录 1、5、10 个实际登录账号下的内存、CPU、切换延迟、网络流量和恢复时间。测试环境、平台网页版本和机器配置一起记录；如果没有足够真实测试账号，容量结论明确标注未覆盖数量。

网站统计和日志使用服务器 UTC 时间，按用户时区显示；设备上报同时带客户端时间和服务端接收时间。角色权限同时约束页面操作与服务端接口，前端按钮隐藏不能替代鉴权。

## 十一 代码管理与发布

项目使用独立 Git 历史，建立阶段标签，例如 `v0.1.0-login`、`v0.2.0-accounts`。新远端仓库地址在首次推送前确定；已恢复的旧代码仅作需求与逻辑参考，不混入旧数据库、运行凭据和浏览器会话。

每个可验收阶段先提交源码和数据库迁移，再从该提交构建网站、服务端和客户端，发布清单记录版本、提交号、文件校验值与迁移版本。生产服务器不直接修改源码来代替提交。

GitHub 备份源码；数据库、导入文件、业务附件和必要运行配置采用独立加密备份。浏览器登录凭据保持本机保存，跨设备迁移使用重新关联流程。外置磁盘上的源码另有内置磁盘或远端副本，避免单一磁盘丢失导致项目中断。

初期可复用现有服务器开设独立开发或测试环境。生产切换、旧数据导入与正式收款接入在对应阶段实施，并保留可恢复的旧环境。
